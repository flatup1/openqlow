## この手順の設計思想

JINは分析と整理が苦手で、常にタスクを抱えている（AIKA_OS_CONSTITUTION §1）。だからこの手順は**毎日5分、週に30分**しか使わない。

- 判断の材料は openQLOW が並べる。
- **決めるのはJINだけ**。ただし決める回数は週に1回に絞る。
- 平日は「詰まりを直す」だけで、考えない。

## 月曜（30分）— 数字を確定して、1つだけ決める

### 手順

1. **数字を出す**（5分）
   ```bash
   npm run crm -- daily-report    # その日のCRMレポートを生成して保存
   npm run crm -- followups       # 追客漏れ・体験後フォロー・口コミ依頼の候補を一覧
   npm run crm -- list            # 見込み客の全件（--status 体験済み などで絞れる）
   ```
   朝ブリーフは本番VPSが自動生成して `DAILY-BRIEF.md` に書き出している。**手元で `npm run morning` を素で実行しない**（本物のLINE送信とVault上書きが起きる）。手元で見たいときは `run-openqlow-dryrun` スキルの環境変数レシピを使う。

   自動で取れない3つ（在籍数・退会数・口コミ件数）を手で数える。

2. **スコアボードを埋める**（10分）
   `20_OPENQLOW_WEEKLY_SCOREBOARD.md §6` の1枚を埋める。空欄を残さない。分からない欄は「不明」と書く（0と書かない）。

3. **詰まっている段階を1つだけ選ぶ**（5分）
   選び方は `22_OPENQLOW_NEXT_ACTION_RULES.md` の判断順に従う。迷ったら**上流を優先**（体験予約 → 入会 → 継続 → 口コミ → 紹介の順で見て、最初に警戒状態に当たった段階を選ぶ）。

4. **来週ひとつだけ変えることを決める**（5分）
   `23_FOUR_WEEK_EXPERIMENTS.md` から、費用と作業量が最も小さいものを選ぶ。

5. **JIN確認事項を書き出す**（5分）
   決められなかったことを次週へ持ち越さず、その場で「確認する」「保留する」を決める。

### 月曜に**やらないこと**
- 新しい施策を2つ以上始める。
- 数字が悪いという理由で値下げを検討する（安売りは禁止事項）。
- 先週の反省を長く書く。

## 毎日5分 — 詰まりの検知だけ

朝でも夜でもよい。**同じ時刻にやる**。

1. **未返信を確認する**
   ```bash
   npm run crm -- followups        # 24時間以上動きのない見込み客
   ```
   1件でもあれば、それが今日の最優先。AIKAの下書きを確認してJINが送る。

2. **今日の体験予約を確認する**
   前日リマインドが必要な人がいれば下書きを用意する。

3. **体験済み・未入会を確認する**
   ```bash
   npm run trial-followup -- --status 検討中
   ```
   翌日フォローの下書きを出す。送信はJIN。

**5分を超えたら止める。** 残りは月曜に回す。毎日考え始めると続かない。

## 日曜（10分）— 振り返り

数字は見ない。次の3つだけ書く。

1. 今週いちばん良かったやりとりは何か（1件だけ）。
2. 今週いちばん詰まったのはどこか（1件だけ）。
3. 来週やめることは何か（1件だけ）。

**「やめること」を必ず1つ書く。** タスクは減らさないと増え続ける（AIKA_OS_CONSTITUTION §2）。

## 数字が悪い場合の判断順

上から順に見て、**最初に当てはまったところで止めて、そこだけ直す**。下まで読まない。

| 順 | 確認 | 当てはまったら |
|---|---|---|
| 1 | 24時間以上の未返信があるか | 返信する。他は何もしない。**これが最優先** |
| 2 | 体験済み・未入会が放置されていないか | フォローの下書きを出してJINが送る |
| 3 | 体験の予約はあるのに実施に至っていないか | 日程確定の速さとリマインドを直す（案内文をいじらない） |
| 4 | 問い合わせはあるが予約に進まないか | 返信の中身を直す。日程候補を添えているか確認 |
| 5 | 問い合わせ自体が少ないか | ここで初めて発信・広告の話をする |
| 6 | 退会が入会を上回っているか | 入口ではなく継続を直す。来館の空いた会員への声かけ |
| 7 | 口コミ依頼を送っていないか | 候補に送る。文面は既にある |
| 8 | 紹介がゼロか | 特典を知らせる。転送できる1通を作る |

**よくある間違い**: 5（集客が足りない）から始めてしまうこと。1〜4が詰まっている状態で問い合わせを増やしても、取りこぼしが増えるだけで売上は増えない。

## 仕事の分担

### AIKAへ渡す仕事（守り・お客様に向く）
- 問い合わせへの一次返信の下書き
- 体験予約の受付（日時は確定しない）
- 退会・休会・料金の規定説明（断定しない）
- 怪我・クレーム・法的な言葉の一次受付とJINへの引き継ぎ
- 事故防止の判断基準は `flatup-ai-os/docs/canon/10_AIKA_SAFETY_CASEBOOK_50.md`

### openQLOWが担当する仕事（攻め・JINに向く）
- CRMの集計と、詰まっている段階の提示
- 追客文・体験後フォロー・口コミ依頼・紹介案内の**下書き**
- SNS投稿・広告文の**下書き**
- 朝ブリーフの生成（本番はDRY-RUN設定で送信せずVaultへ保存）
- 週次スコアボードの材料集め

**openQLOWがしないこと**: お客様への送信、自動返信、顧客メールの自動受信、予約確定、料金・返金・退会の処理。これらは `src/safety/forbidden_actions.ts` で実装レベルに禁止されている。

### 人間（JIN）だけが決める仕事
- すべての送信・投稿・配信
- 体験日時の確定、入会手続き
- 料金・返金・退会・休会・違約金の確定
- 値引きとキャンペーンの可否
- クレームの最終回答、法的な対応
- 週にひとつ変えることの決定
- 本番反映、Vault・GitHubの重要変更
