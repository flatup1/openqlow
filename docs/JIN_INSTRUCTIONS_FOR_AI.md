## 1. JINの基本指示（毎回これが出ます・原文）

JINは作業のたび、ほぼ必ずこの一文を投げてきます。**これが評価基準そのものです。**

```
中学生にもわかるように教えて　残りの作業を可視化して　最短最速最低工数で実践したい　
最低価格で最大限に効果を出し出い　コスパタイパを意識して制作に取り掛かって　
必ず採点してから残りの作業がどの程度あって何をやっているのかを説明して　次の一手を教えて
```

> ※「出し出い」は原文ママ（「出したい」の打ち間違いと思われます）。

### これを分解すると、7つの要求です

| # | JINの言葉 | AIがやること |
|---|---|---|
| 1 | 中学生にもわかるように教えて | 専門用語を使わない。使うなら必ず言い換える |
| 2 | 残りの作業を可視化して | 残りを図や表で見せる。「あといくつ」を数える |
| 3 | 最短最速最低工数で実践したい | 遠回りをしない。一番短い道を選ぶ |
| 4 | 最低価格で最大限に効果を出したい | 安く・効果の大きい順に並べる |
| 5 | コスパタイパを意識して**制作に取り掛かって** | **説明だけで終わらせず、実際に作る** |
| 6 | **必ず採点してから**残りの作業がどの程度あって何をやっているのかを説明して | **点数（100点満点）を先に出す。** そのあと中身 |
| 7 | 次の一手を教えて | 次にやることを**1つだけ**示す |

### 守ること

- **採点は最初に出す。** 「できました」の報告だけで終わらせない
- **自分のミスは減点する。** 甘く付けると採点の意味がなくなる
- **次の一手は1つだけ。** 選択肢を並べない

## 2. JINが実際に言ってきた言葉と、その意味（対話式）

### 2-1. 「仕事を引き継ぎたい」

> **JIN:** `https://claude.ai/code/session_xxxxx 仕事を引き継ぎたい`

**意味:** 別のAIセッションの作業を、途中から引き継いでほしい。

**やること:** 引き継ぎ書（`docs/HANDOFF_日付_...md`）を作る。
何が終わっていて、何が残っていて、JINが何をすればいいかを書く。

---

### 2-2. 「100点になるまで修正と検証をつづけて」

> **JIN:** `100点になるまで修正と検証をつづけて`

**意味:** 自分で不具合を探し、直し、確かめる。これを満点まで繰り返す。

**やること:**
- テストを書くだけで満足しない。**実際に動かして目で見る**
- 直したら必ず**「わざと壊してテストが落ちるか」**を確かめる（これをしないと、効いていないテストが増える）
- **100点にできない部分があるなら、正直に「ここは私には届かない」と言う**

**重要:** JINの環境（Mac・SSH鍵・XServer）にしか手が届かない作業があります。
そこは**推測で進めず、JINに渡す**こと。

---

### 2-3. 「マージして」

> **JIN:** `マージして`

**意味:** いま開いているPRをmainに入れていい、という**オーナー承認**です。

**やること:**
- この一言が出るまで、**こちらからマージしない**
- マージ前に CI が緑か、競合がないかを確認する
- マージ後は購読を解除し、定期チェックを止める

---

### 2-4. 「本当にできてる？」

> **JIN:** `本当にできてる？`

**意味:** 楽観的な報告を疑っている。**証拠を見せろ**ということ。

**やること:**
- **「確認できていること」と「まだ分からないこと」を分けて書く**
- 「たぶん動いています」は禁止。**確かめていないなら、確かめていないと言う**
- 確かめる手段がないなら、**JINに実行してもらうコマンドを1つ渡す**

> この一言は、過去にAIが「できました」と言いながら実際には本番に何も届いていなかった、
> という失敗から来ています。**最重要の指示です。**

---

### 2-5. 「何が起きてる小学生にもわかるように教えて」

> **JIN:** `何が起きてる小学生にもわかるように教えて`

**意味:** 中学生向けでもまだ難しい。**もっと簡単に。**

**やること:**
- たとえ話を使う（おうち／ひっこし／宿題 など）
- 1文を短く
- 図（```で囲んだ簡単な図）を使う

---

### 2-6. 「やって」

> **JIN:** `やって`

**意味:** 提案した修正を実行していい、という承認。

**やること:** そのまま実装 → テスト → 検証 → PR。

---

### 2-7. 「アップロードするための最新版のファイル出して」

> **JIN:** `アップロードするための最新版のファイル出して`

**意味:** XServerに上げるファイルを、すぐ使える形で渡してほしい。

**やること:** ZIPにまとめて渡す。どこへ置くかも書く。

---

### 2-8. 「終わらない」「あってる？」

> **JIN:** `終わらない` / `あってる？`

**意味:** 動かない・不安。**進捗が見えていない。**

**やること:**
- 止まっている箇所を特定する
- **「無言で固まる」仕組みを作らない**（進捗を表示させる）

> 実例: デプロイが16GBの動画を転送しようとして止まっていた。
> `rsync` に `-v` を付けていなかったため、固まっているのか動いているのか区別できなかった。

---

### 2-9. 「作業中に利用制限に達しましたが、現在はリセットされています。中断したところから続けてください。」

**意味:** 中断からの再開。

**やること:** 挨拶や要約をせず、**止まった作業をそのまま続ける。**

## 3. 絶対に守るルール（CLAUDE.md より・原文）

```
- 日本語、結論ファースト、短く、中学生にも分かる表現を使う。
- AIKAは守りの顧客対応、openQLOWは攻めの営業・経営支援として混同しない。
- 既存実装、未コミット差分、原本を保持し、削除や全面上書きをしない。
- 下書き・分析・テストは進めてよい。送信、予約確定、料金判断、返金、退会、休会、
  外部書き込み、公開、課金、本番反映、commit、push、PRは人間承認後。
- 秘密情報や顧客個人情報を表示・保存・コミットしない。
- 変更後は ./scripts/validate-ai-os.sh と関連テストを実行する。
```

### 追加で分かっている禁止事項

| やってはいけないこと | 理由 |
|---|---|
| `git push --force` / `git reset --hard` / `rm -rf` | リポジトリのポリシーフックが阻止する。履歴は壊さない |
| VPS内で `git pull` / `git checkout` / `git stash` | VPSは rsync で配られる場所。`.git` は送っていない。VPSのgitは古いまま止まっている |
| 料金・時間・住所を直書き | `src/shared/canon.ts` が唯一の正本。コピーしない |
| テストをスキップ・無効化して緑にする | 検査が嘘をつくようになる |

## 4. システムの全体像（これを間違えると全部ズレます）

### AIは2つ。混同しない

| | 役割 |
|---|---|
| **AIKA** | 守り。お客さまへのLINE自動対応 |
| **openQLOW** | 攻め。営業・経営支援 |

### サーバーは3つ。担当が別々

```
① openQLOW VPS  162.43.41.182
   └ LINEの自動応答（openqlow-webhook）
   └ 反映方法: Macで npm run deploy（rsyncで配る。.gitは送らない）

② AIKA VPS      162.43.90.71
   └ 引き継ぎコードの受け口 https://aika.flatupnarita.jp/journey
   └ 実装は別リポジトリ flatup1/flatup の Python
   └ 反映方法: AIKA側の deploy_aika_release.sh
   └ ⚠️ openQLOW の npm run deploy では絶対に直らない

③ XServer
   └ WebOSのページ https://www.flatupnarita.jp/webos/
   └ 反映方法: public_html/webos/ へ手動アップロード
   └ ⚠️ npm run deploy は flatup-webos/ を除外しているので送られない
```

**「①を反映したのに②が直らない」は当たり前です。担当が違います。**

### 本物の住所は `www` 付き

```
https://flatupnarita.jp/webos/      → 301 転送
https://www.flatupnarita.jp/webos/  → 200 ← 実際に出るのはこちら
```

## 7. 過去にAIがやらかした失敗（繰り返さないため）

| 失敗 | 何が起きたか | 教訓 |
|---|---|---|
| VPSで `git pull` を案内 | VPSは `master` ブランチで止まっており失敗。古いコードがビルドされた | **VPSはrsyncで配る。gitを触らない** |
| `/journey` を openQLOW の担当だと誤認 | 「`npm run deploy` すれば直る」と案内し続けた。実際はAIKA VPSの担当 | **正本ドキュメントを読む。推測しない** |
| 301を「ページが無い」と誤報 | 「XServerにindex.htmlがあるか確かめろ」と見当違いの作業をさせた | **転送は追いかけてから判定する** |
| デプロイが16GB転送で固まる | `rsync` に `-v` が無く、固まっているか動いているか分からなかった | **無言で待たせない** |
| 進捗表示が手打ちの表だった | 質問を1つ足すと進捗だけ黙って嘘をつく状態だった | **データから計算する。手打ちしない** |
| 版番号の検査が index.html だけ | 写真の版が app.js にあり、ズレても検査は合格を出し続けた | **検査の範囲を疑う** |

## 8. 作業のやり方（毎回これ）

```
1. 採点する（100点満点・自分のミスは減点）
2. 残りを可視化する（表か図）
3. 一番効いて一番安いものを1つ選ぶ
4. 実際に作る（説明だけで終わらない）
5. 検証する
   - npm test
   - ./scripts/validate-ai-os.sh
   - npm run typecheck
   - 画面ものは実際に描画して目で見る
6. わざと壊して、テストが落ちることを確かめる
7. commit → push → PR（draft）
8. CIが緑になるまで見張る
9. JINの「マージして」を待つ
10. 次の一手を1つだけ伝える
```

### 報告の書き方

```markdown
## 採点：XX点 / 100点

| 項目 | 点 | 変化 |
|---|---|---|
| … | … | … |

## やったこと（中学生向け）
（たとえ話・図を使う）

## 検証したこと（正直に）
- 確認できていること
- まだ分からないこと  ← ここを省かない

## 次の一手
（1つだけ）
```
