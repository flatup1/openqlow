## 全体の流れ（Android）

```
1. グラスの電源が入る
        ↓
2. アプリがBLEでグラスを見つける            ← 未確認: 広告名の形式
        ↓
3. BLE接続する                              ← 参考: Service UUID 7905FFF0-B5CE-4E99-A40F-4B1E122D00D0
        ↓
4. 電池残量を読む                            ← 未確認: コマンド
        ↓
5. 「転送モードにして」とBLEで命令する         ← 未確認: コマンド
        ↓
6. グラスがWi-Fiを立てる
        ↓
7. スマホがグラスのWi-Fiにつなぐ（Wi-Fi Direct）← 未確認: IPアドレスの決まり方
        ↓
8. http://<グラスIP>/files/media.config を取る ← 未確認: 応答の形式
        ↓
9. まだ持っていないファイルだけを選ぶ           ← ここは core の仕事（実機不要）
        ↓
10. 1つずつダウンロードして端末に保存           ← 未確認: Range対応の有無
        ↓
11. 進み具合を表示する                        ← ここは core の仕事（実機不要）
        ↓
12. 切れたら、続きから再開する                 ← ここは core の仕事（実機不要）
```

**9・11・12 が `core` の担当です。ここは実機なしで作れて、テストもできます。**
それ以外は実機がないと確定しません。

## iOSの違い

iOSには Wi-Fi Direct がありません。要件書§5によると、グラスが**普通のWi-Fiアクセスポイント**を出す方式を使います。

```
5'. BLEで Wi-Fi の SSID とパスワードを聞き出す   ← 未確認: コマンド
6'. NEHotspotConfiguration でそのWi-Fiにつなぐ
7'. 「今はインターネットが使えません」と画面で説明する  ← 要件書§10
8'. 以降はAndroidと同じ（HTTPで一覧取得→ダウンロード）
```

必要になるもの（未確認・要調査）: Info.plist のローカルネットワーク利用説明、`NSLocalNetworkUsageDescription`、Hotspot Configuration の Entitlement。

## core が担当する4つの処理

### 1. メディア一覧の解析

グラスから受け取った `media.config` を、アプリが扱える形に変換します。

```
入力: media.config の中身（形式は未確認）
出力: MediaItem のリスト
      - id        … ファイルを一意に決めるもの
      - name      … ファイル名
      - type      … 写真 / 動画
      - sizeBytes … バイト数
      - createdAt … 撮影日時
      - url       … ダウンロード先
```

**未確認なので、こう作ります**: 解析処理を差し替え可能にしておき、実機で本物の応答が取れた時点で
その1形式だけを実装します。今は「解析結果 → 以降の処理」の部分を先に固めます。

### 2. 重複防止

同じ写真を二重に保存しない仕組みです。要件書§10・§17の必須項目です。

- 転送前: `id` が既に保存済み一覧にあれば**飛ばす**
- 転送後: ファイルサイズを照合し、記録に残す
- `id` が信用できない機種だった場合に備え、`名前 + サイズ + 撮影日時` の組み合わせでも判定できるようにする

### 3. 途中再開キュー

要件書§10「接続が切れても、すでに転送済みのデータを消さない」の中身です。

各ファイルは次の状態を持ちます。

```
待機中 → 転送中 → 完了
              ↓
            保留（あとで再試行）
              ↓
            失敗（理由つき）
```

**壊れたファイルを作らない方法**（要件書§10）

1. ダウンロードは `xxx.jpg.part` という**一時ファイル**に書く
2. 最後まで受け取れて、サイズが一致したときだけ `xxx.jpg` に名前を変える
3. 途中で切れたら `.part` は残す。再開時は続きから（HTTP Range が使えれば）
4. Range が使えない機種なら `.part` を消して、そのファイルだけ最初からやり直す

**Range 対応は未確認**です。両方の道を用意しておきます。

### 4. エラー分類

要件書§10「容量不足、通信切断、Wi-Fi接続失敗、HTTPエラー、権限不足を区別する」。
そして「エラー表示には必ず次の操作を付ける」。

| 種類 | 画面に出す言葉（案） | 次にすること |
|---|---|---|
| 容量不足 | 「スマホの空き容量が足りません」 | 「いらない写真を消す」ボタン |
| 通信切断 | 「途中で切れました。続きからやり直せます」 | 「もう一度つなぐ」ボタン |
| Wi-Fi接続失敗 | 「グラスのWi-Fiにつながりませんでした」 | 「グラスを近づけて、もう一度」 |
| HTTPエラー | 「グラスが写真を渡せませんでした」 | 「グラスの電源を入れ直す」案内 |
| 権限不足 | 「アプリに許可が必要です」 | 設定画面を開くボタン |
| Bluetoothオフ | 「Bluetoothがオフです」 | オンにする手順を表示 |
| グラス未発見 | 「グラスが見つかりません」 | 電源と距離の確認案内 |

**原則**: 「失敗しました」だけで終わらせない。必ず「次にどうするか」を大きく出す。

## 安全とプライバシー（core の段階から守る）

要件書§16の内容を、コードの決まりごとにします。

- Wi-Fiのパスワードを**ログに出さない**。ログに出す前にマスクする処理を core に入れる
- 写真の**中身をログに出さない**。出すのは件数と種類だけ
- ファイル名も、必要以上にログへ残さない
- 写真・動画を**外部へ送信する処理を core に一切書かない**（サーバーなし）
- 大きな動画は**丸ごとメモリに読まない**。ストリーミングで書き込む

## 実機で最初に確認すること（Phase 1-C の入口）

この5つが取れれば、未確認事項の大半が消えます。

1. グラスのBLE広告名と、実際に見えるService UUID
2. 転送モードを起動するBLEコマンドのバイト列
3. Wi-Fi接続後のグラスのIPアドレス
4. `http://<IP>/files/media.config` の**生の応答**（そのまま保存する）
5. 画像1つに `Range: bytes=0-1023` を付けたときの応答コード（206なら再開が使える）
